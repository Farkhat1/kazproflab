# Размещение самостоятельного сайта

Сайт собирается в статические файлы. Node.js и браузер нужны только на компьютере, где выполняется сборка; на хостинге достаточно Apache 2.4 или Nginx. Для публикации используются файлы из `website/dist/client`, включая скрытый `.htaccess`. Папки `src`, `node_modules`, `content-source` и весь рабочий проект на хостинг загружать не нужно.

## Сборка

Используйте Node.js 22 и установленные зависимости проекта. Из папки `website`:

```sh
npm ci
npm run build
npm run test:sites
```

`npm run build` включает `scripts/prerender.mjs`, отдельно запускать его не требуется. Повторный запуск поддерживается. При ошибке генерации HTML не публикуйте частичную сборку.

На Windows скрипт использует установленный Microsoft Edge. На Linux/CI установите браузер командой `npx playwright install chromium`. Можно явно задать `PRERENDER_BROWSER_CHANNEL` (например, `chrome`) или `PRERENDER_BROWSER_EXECUTABLE` с путём к браузеру. Пакет `playwright` берётся из зависимостей проекта; `PLAYWRIGHT_PACKAGE_PATH` позволяет указать существующий пакет вручную. `PRERENDER_WORKERS` задаёт количество параллельных страниц (по умолчанию 3).

Все адреса берутся из `src/data/site-data.json`, поэтому папка `website` собирается самостоятельно. Сборка сохраняет исходные пути: карточки услуг с `.html` становятся файлами с точным именем, а адреса без расширения — папками с `index.html`. Например, `/contacts` соответствует `dist/client/contacts/index.html`.

Prerender открывает производственную сборку, ждёт появления содержимого и загрузки шрифтов, затем записывает HTML с полным содержимым страницы и метаданными. Тексты и ссылки доступны без обязательного выполнения JavaScript. JavaScript подключает поиск, меню и другие интерактивные элементы. Приложение должно использовать `hydrateRoot`, когда `#root` содержит сохранённую разметку.

Для проверки готовой сборки запустите `node scripts/serve-static.mjs` и откройте `http://127.0.0.1:4174`. Этот сервер правильно обслуживает исходные адреса без расширения и возвращает настоящие 404. Порт и адрес меняются аргументами `--port 4174 --host 127.0.0.1`. По умолчанию сервер предварительного просмотра добавляет `X-Robots-Tag: noindex, nofollow`; переменная `PREVIEW_NOINDEX=0` отключает только этот заголовок. Эти настройки не меняют опубликованные HTML-файлы.

Дополнительно создаются:

- `dist/client/sitemap.xml` — все исходные URL;
- `dist/client/robots.txt` — доступ поисковых роботов и адрес карты сайта;
- `dist/client/.htaccess` — сохранение адресов без завершающего слеша и настоящие ответы 404 на Apache;
- `dist/client/404.html` — отдельная страница для неизвестных адресов;
- `dist/prerender-manifest.json` — отчёт с заголовками, описаниями и объёмом текста каждой страницы.

Canonical и sitemap по умолчанию указывают на `https://kazproflab.kz`. Переменная `SITE_URL` переопределяет домен для другого реального сайта. Для тестовой копии оставьте основной canonical, ограничьте доступ паролем или задайте на тестовом сервере заголовок `X-Robots-Tag: noindex`, чтобы она не индексировалась.

## Netlify / временный адрес для согласования

Конфигурация находится в `../../netlify.toml` и применяется при импорте GitHub-репозитория. Base directory — `website`, build command — `npm run build:netlify`, publish directory — `dist/netlify`, Node.js — `22`. Выберите ветку `main`; секреты и серверные переменные для этого статического сайта не нужны.

`build:netlify` устанавливает Chromium командой `playwright install chromium`, запускает обычную сборку, подготавливает отдельный пакет и проверяет его. Флаг `--with-deps` намеренно не используется: установка системных библиотек требует root и может завершиться ошибкой в Netlify. Linux-среда Netlify должна содержать системные библиотеки Chromium; это окончательно проверяется при первой облачной сборке.

`scripts/prepare-netlify.mjs` копирует готовые файлы из `dist/client` в `dist/netlify`. Например, исходный `/contacts/index.html` становится `contacts.html`: Netlify с выключенными Pretty URLs обслуживает такой файл по `/contacts`, не добавляя слеш. Имена карточек услуг `p….html` остаются прежними. `.htaccess` не копируется, так как правила Apache на Netlify не действуют. Обычный пакет `dist/client` для казахстанского Apache/Nginx остаётся без изменений.

Три проверки `npm run test:netlify` сверяют содержимое всех 59 страниц и их canonical, двоичную идентичность ресурсов и наличие отдельного `404.html`. Любая ошибка останавливает сборку до публикации. Не добавляйте `/* /index.html 200`: неизвестные адреса должны сохранять ответ 404.

В конфигурации Netlify отключены Pretty URLs и установлен `X-Robots-Tag: noindex, nofollow` для временной копии. Это относится в том числе к основной ветке проекта на `netlify.app`; сама конфигурация не подключает `kazproflab.kz`.

Официальные справочники: [конфигурация Netlify](https://docs.netlify.com/build/configure-builds/file-based-configuration/), [обработка URL](https://docs.netlify.com/build/post-processing/overview/), [установка браузеров Playwright](https://playwright.dev/docs/browsers).

## Apache / обычный хостинг

1. Создайте отдельную тестовую папку или тестовый поддомен на хостинге.
2. Загрузите содержимое `dist/client` в корень сайта, включая `.htaccess`. Не загружайте саму папку `client` как вложенный каталог.
3. Проверьте, что включён `mod_rewrite`, разрешены правила `.htaccess` и работают директивы `Options`/`DirectorySlash`. Если хостинг запрещает отдельную директиву, перенесите её в настройки виртуального хоста через поддержку хостинга.
4. Проверьте открытие `/`, `/contacts`, одной категории и карточки услуги с `.html` напрямую и после обновления страницы. Неизвестный адрес должен возвращать статус HTTP 404.
5. Подключите TLS-сертификат и перенаправление HTTP → HTTPS, а также `www.kazproflab.kz` → `kazproflab.kz` средствами панели хостинга.

Правила не перенаправляют неизвестные адреса на главную: это позволяет поисковым системам правильно распознавать отсутствующие страницы. Адреса `/contacts/` и аналогичные перенаправляются на исходный `/contacts`.

## Nginx

Пример настроек — в `nginx.conf`. Задайте актуальный путь в `root` и включите этот сервер в конфигурацию хостинга. SSL-сертификат и перенаправление на HTTPS настраиваются отдельно в панели или конфигурации сервера. Правило `try_files` должно проверять `$uri/index.html`, чтобы адреса без расширения отдавали соответствующую HTML-страницу.

## Перед переключением домена

Проверьте новый сайт на временном адресе: все исходные страницы, меню на телефоне, поиск, телефонные ссылки, WhatsApp и адрес электронной почты. Сравните количество исходных страниц с `pageCount` в отчёте prerender. Отключите JavaScript в браузере и убедитесь, что главная, категория и услуга сохраняют свой текст.

Затем подготовьте DNS-записи нового хостинга, сохранив существующие записи почты. Не меняйте MX и связанные TXT-записи при простом переносе сайта. Старый сайт должен работать до проверки новой версии и согласованного переключения. После переключения проверьте HTTPS, основные адреса и sitemap на основном домене.

Сборка сама ничего не публикует, не меняет DNS и не отключает Satu.
